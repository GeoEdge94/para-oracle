# M1 — Normalisation canonique + WeatherPipeline + adaptation SpectralPipeline

**Date** : 2026-04-22
**Statut** : ✅ Implémenté, testé en isolation ET validé E2E sur Docker.

## Objectif

Poser le socle commun pour le pipeline Web3 : une interface de résultat partagée
entre les pipelines, la normalisation JSON canonique + fingerprint SHA-256, et le
nouveau `WeatherPipeline` (ERA5-Land). Adapter `SpectralPipeline` en non-breaking
pour qu'il émette le même type de manifest.

## Choix techniques

- **Float precision à 6 décimales** : via recursive `_round_floats()` avant
  `json.dumps`. Pas de format fixed-width (`"%.6f"`) car Python's `json` utilise
  le shortest round-trip repr — `1.0` reste `"1.0"`, consistent cross-run sur
  même Python. Suffisant pour MVP Python-only. v2 pour cross-language :
  passer à `Decimal` ou format fixed-width.
- **Séparation canonical / schema_v1** : `schema_v1.py` contient le schéma de
  validation (JSON Schema), `canonical.py` contient les règles de sérialisation.
  Les deux ne doivent jamais être modifiés ensemble sans bumper à v2.
- **Stratégie blobs pour SpectralPipeline** : les rasters `.tif` sont binaires
  (~1-20 Mo chacun). Au lieu de les sérialiser en JSON, on les pinne comme blobs
  IPFS séparés et on référence leurs CIDs dans `fingerprint_inputs.rasters[]`.
  Le manifest JSON reste léger. Les CIDs sont `None` à la sortie du pipeline —
  `web3_publisher` (M2) les remplira après pinning.
- **`bet_slug:variable` comme seed** : pour WeatherPipeline. Rester cohérent avec
  `bet_slug:index_type` de SpectralPipeline. Deux paris sur la même zone/période
  mais variables différentes ont des valeurs mock différentes.
- **Double-write des champs legacy** : les 5 colonnes `ndvi_*_hash` et `ipfs_cid`
  continuent d'être remplies pour les paris spectral. Frontend legacy reste
  fonctionnel. Nouvelles colonnes (`data_cid`, `script_cid`, ...) arrivent en M2.
- **Pas de colonnes dédiées weather dans `analyses`** : on réutilise
  `surface_deforestee_km2` pour `observed_value` (rename reporté pour ne pas
  casser le frontend). Les autres colonnes spectral restent NULL pour les bets
  weather.

## Tests

### Canonical module (stdlib only)

```bash
python -c "
from app.services.canonical import canonicalize, fingerprint_sha256
# ordering deterministic
assert canonicalize({'b':2,'a':1.123456789}) == canonicalize({'a':1.123456789,'b':2})
# float rounding to 6 decimals
assert canonicalize({'x':1.2345678999}) == b'{\"x\":1.234568}'
# fingerprint stable across key ordering
assert fingerprint_sha256({'a':1,'b':[1.0,2.0]}) == fingerprint_sha256({'b':[1.0,2.0],'a':1})
"
```

## Points ouverts / à surveiller

- **Docker E2E non lancé** : Docker Desktop pas démarré au moment de l'impl.
  Nécessaire avant de passer à M2.
- **CDS real retrieve** (`cds_client._real_retrieve`) est en `NotImplementedError`.
  À faire en M1bis avant d'avoir du vrai fingerprinting non-mock.
- **`_round_floats` rounding mode** : Python utilise banker's rounding
  (`1.5 → 2`, `2.5 → 2`). Noter ça si cross-language verification devient requis.
- **Les blobs sur disque** : `spectral_pipeline` écrit dans `DATA_DIR/rasters/<slug>/`.
  En M2, le web3_publisher devra les pinner avec un `IPFSClient.pin_file(path)`.
- **`OracleResult.surface_deforestee_km2`** : nom trompeur pour les bets weather
  (valeur en mm, pas km²). Rename à `observed_value` prévu en M4 (frontend).
