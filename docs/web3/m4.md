# M4 — Challenge bot + TLSNotary stub + E2E dispute flow

**Date** : 2026-04-22
**Statut** : ✅ Bot challenger standalone (zero import `app.*`), TLSNotary stub
pinne + reference dans le fingerprint, endpoint `/oracle/pending` pour feed
public, script E2E bash `scripts/e2e_challenger.sh` (match + dispute).
**Mode** : mock-first — `USE_MOCK_TLSNOTARY=true`, `USE_MOCK_IPFS=true`,
`USE_MOCK_CHAIN=true` par defaut.

## Objectif

Fermer la boucle "quiconque peut verifier l'oracle" :
1. A chaque resolution, le backend pin une **TLSNotary proof** (stub) qui
   atteste que la requete source (CDS pour weather, STAC pour spectral) n'a
   pas ete alteree. Le CID de la proof entre dans le fingerprint canonique.
2. Un endpoint public `GET /oracle/pending` expose tous les pointeurs
   necessaires a la re-verification (3 CIDs + fingerprint attendu + tx_hash +
   fenetre de dispute).
3. Un **bot challenger open-source** (container separe, deps minimales) poll
   cet endpoint, re-telecharge `data.json` depuis IPFS, re-execute
   `resolution_script.py` et compare fingerprint + outcome. S'il diverge, il
   log DISPUTE (en M4bis il appellera `contract.dispute()`).
4. Le frontend affiche les 3 CIDs, le tx_hash (lien Polygonscan Amoy), et un
   countdown temps reel de la fenetre de dispute.

## Choix techniques

- **Bot standalone = container separe, zero app.\*** : deliberement. Le bot
  doit pouvoir etre cloné, built et lancé par un tiers SANS avoir a
  installer le backend, la DB ou les deps scientifiques (rasterio, etc).
  Image finale ≈ 60 MB (python-slim + httpx). Dans le futur on pourra
  extraire `bot/` dans son propre repo public `paraoracle-challenger`.
- **`--once` retourne 1 si ≥1 dispute** : permet au script E2E de verifier
  directement l'exit code sans parser stdout.
- **TLSNotary dans le fingerprint** : decision importante. `tls_proof.cid`
  entre dans le manifest **avant** le calcul du fingerprint final. Donc le
  fingerprint (et donc `resolution_id` on-chain) est different entre une
  resolution avec stub et une future avec vraie PSE proof — on peut
  distinguer les deux regimes on-chain sans migration.
- **`signed_at` stub deterministe** : derive des 32 premiers bits du SHA-256
  du contenu (server + url + bodies). Garantit qu'un re-run byte-identique
  produit le meme fingerprint. En real PSE, le timestamp sera signe par le
  notaire — divergence acceptable puisque le fingerprint changera avec
  l'arrivee de la vraie proof.
- **`request_body` pour spectral = `b""`** : le `SpectralPipeline` ne
  preserve pas actuellement la requete STAC brute. On notarize donc
  seulement la response (liste des rasters). Limite acceptable en mock ;
  a ameliorer en M4bis (persister la request STAC pour que la proof
  couvre les deux moities).
- **Gateway fallback dans `_fetch_data_json`** : le bot essaie d'abord
  `MOCK_IPFS_DIR/<cid>` (montage volume), puis fallback HTTP gateway.
  Permet le dev local sans Pinata ET le deploiement prod identique avec
  juste un `IPFS_GATEWAY_URL` different.
- **Helpers E2E dans le container backend** : l'hote Windows (git-bash) n'a
  ni python3 ni jq fiables. Tous les traitements JSON passent par `docker
  compose exec -T backend python3 /scripts/_e2e_helpers.py ...`. Le script
  bash E2E reste portable Mac/Linux/Windows.
- **Bot image minimale, CMD = poll loop** : par defaut le bot tourne en
  boucle (pour demo "live"). Le `--once` est utilise par le script E2E.
- **Fingerprint verification via resolution_script.py subprocess** : le
  bot ne reimplemente PAS `canonicalize()`. Il telecharge la meme copie
  immuable de `resolution_script.py` (via volume en dev, via gateway en
  prod) et l'execute. C'est le meme code que celui publie on-chain via
  `script_cid`. Garantie forte : une divergence entre bot et backend est
  forcement une divergence de DONNEES, pas d'algorithme.

## Tests

### Bot standalone (local)

```bash
# 1. Stack up
docker compose up -d db backend
docker compose --profile bot build bot

# 2. Une resolution existe deja (M3 ou un POST /oracle/resolve)
curl -s http://localhost:8000/oracle/pending?limit=5 | jq '.items[0]'

# 3. Bot une passe
docker compose --profile bot run --rm bot python challenger.py --once --limit 5
```

Exit 0 + logs `[OK] <slug>: match (fingerprint + outcome) | expected=...`.

### E2E scenario (match + tamper + dispute)

```bash
docker compose up -d db backend
docker compose --profile bot build bot
bash scripts/e2e_challenger.sh precip-amoy-testnet-01
```

Attendu :

```
=== 1. Reset bet precip-amoy-testnet-01 ===
  done
=== 2. POST /oracle/resolve/precip-amoy-testnet-01 ===
  resolved_outcome = YES|NO
  fingerprint      = sha256:...
  data_cid         = bafybei...
=== 3. GET /oracle/pending ===
  data_cid    = bafybei... (meme)
  expected_fp = sha256:... (meme)
=== 4. Run challenger bot (expect MATCH, exit 0) ===
  [OK] precip-amoy-testnet-01 (...): match (fingerprint + outcome) ...
  [challenger] summary: 1 match / 0 dispute
  bot exit = 0
=== 5. Tamper data.json (flip observed_value) ===
  orig=X.Y tampered=(X+9999).Y
=== 6. Run challenger bot (expect DISPUTE, exit 1) ===
  [DISPUTE] precip-amoy-testnet-01 (...): fingerprint mismatch (mismatch) ...
  [challenger] summary: 0 match / 1 dispute
  bot exit = 1
=== 7. Restore original data.json ===
  restored

=== E2E CHALLENGER: PASS ===
```

- M3 Foundry tests : attendu **14/14 passed** (pas de modif contrat).
- M1 spectral tests : attendu **28/28 passed**.

## Points ouverts / TODO M4bis

- **Real `_real_proof`** (tlsnotary_client.py) : brancher notaire PSE via
  WebSocket + protocole MPC. La structure stub est deja alignee, l'impact
  sur le manifest sera nul a part le remplacement du champ `signature` et
  `notary.pubkey`.
- **Real `_real_submit`** (chain_client.py) : carryover M3. Web3.py +
  contract ABI + Amoy deployment.
- **Persister la request STAC spectral** : pour que la TLS proof spectral
  couvre les deux moities (pour l'instant seulement les rasters). Necessite
  un buffer dans `SpectralPipeline.run()` qui capture le body POST STAC.
- **Listener d'events on-chain** : le bot aujourd'hui log DISPUTE, mais en
  M4bis il devra appeler `contract.dispute(resolutionId)` avec une
  `CHALLENGER_PRIVATE_KEY` fondee. Ajouter `web3==7.5.0` aux deps bot (mais
  toujours pas `app.*`).
- **Feed pagination** : `/oracle/pending` retourne 50 items max. Ajouter
  `?after=<executed_at>` pour un cursor si la DB grossit.
- **Bot metrics** : exposer un endpoint `/metrics` Prometheus (match count,
  dispute count, last poll timestamp) quand le bot tournera en prod.
- **Bundle bot dans un repo public** : `paraoracle-challenger` GitHub
  template pour que les tiers puissent le lancer sans clone du monorepo.
- **Gateway Pinata en prod** : aujourd'hui `IPFS_GATEWAY_URL` default
  `https://gateway.pinata.cloud/ipfs/`. Verifier les quotas free tier
  quand la demo Amoy tournera publiquement.
