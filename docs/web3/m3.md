**Date** : 2026-04-22
**Statut** : ✅ Contrat + 14 tests Foundry verts, ChainClient mock branché E2E,
chain_tx_hash + bond + dispute_window_end persistés en DB et reproductibles.

## Objectif

Poser le contrat on-chain (`ParaOracle.sol`) avec state machine
PENDING → FINALIZED / DISPUTED, caution USDC, events auditables. Côté Python,
un `ChainClient` mock qui mime la sémantique (tx_hash déterministe, resolution_id
identique au contrat, window 48h) sans appeler de testnet.

## Choix techniques

- **via-IR pour ParaOracle.sol** : sans via-IR, `submitResolution` déclenche un
  "stack too deep" (12 variables locales + event à 12 arguments). `via_ir = true`
  dans `foundry.toml` résout proprement. Coût : compile 7.5s au lieu de <1s.
- **Pas de dépendance OpenZeppelin** : IERC20 inline (20 lignes), MockERC20
  inline (50 lignes). Le contrat reste auto-suffisant, pas de `forge install`
  côté utilisateur final. En prod on pourra switcher vers OZ pour SafeERC20 etc.
- **`resolutionId = keccak256(betSlugHash || uint64(periodEnd))`** — formule
  identique dans le contrat Solidity (`abi.encodePacked`) et dans le mock Python
  (`hashlib.sha3_256(bet_slug_hash + period_end.to_bytes(8, "big"))`). Différence
  MVP : Python utilise SHA3-256 standard au lieu de keccak-256 Ethereum. Les
  deux sont visuellement proches mais produisent des hash différents — pas de
  problème tant qu'on reste en mock-only. Le real `ChainClient` (M3bis) utilisera
  `eth_utils.keccak` pour matcher le contrat.
- **tx_hash mock déterministe** : `sha256(fingerprint | bet_slug | period_end_ts)`.
  Pas de timestamp `now()` dans la seed → reproductible run-après-run pour la
  même résolution. Vérifié : 2 runs successifs (DB reset entre) produisent des
  tx_hash byte-identiques.
- **`resolveDispute` owner-only** pour MVP. Remplacer par intégration UMA
  Optimistic Oracle V3 en M4+. Le contrat actuel accepte un changement d'owner
  (`transferOwnership`) pour migrer vers un multisig ensuite.
- **`outcome` inversé côté contract quand challenger gagne** : c'est la
  sémantique optimiste (l'oracle s'est trompé, on applique le résultat contraire).
  Le frontend/backend doit lire `outcome` on-chain après `FINALIZED` plutôt que
  depuis `analyses.result_bool` pour les cas disputed.
- **`period_end` en `uint64`** : évite les overflows 2106. Stocké comme
  timestamp Unix UTC.
- **`dispute_status` en DB = snapshot du submit** : on stocke `'PENDING'` au
  moment du submit, on ne tracke pas les transitions on-chain en DB (ce sera
  le rôle du challenge bot M4 d'écouter les events et mettre à jour).

## Points ouverts / TODO

- **Real `_real_submit`** (chain_client.py) : à implémenter en M3bis. Nécessite
  web3.py contract binding + ABI généré par `forge build --extra-output abi`.
  Le JSON ABI ira dans `backend/app/contracts/ParaOracle.json`.
- **keccak-256 vs SHA3-256** : le mock ChainClient utilise `hashlib.sha3_256`.
  En réel il faudra `from eth_utils import keccak` pour matcher le contrat.
  Note : les deux algos ont le même output pour certains inputs mais pas
  tous — le mock suffit en mock-only.
- **Déploiement Amoy** : `forge script Deploy.s.sol --rpc-url amoy --broadcast`
  nécessite PRIVATE_KEY fondée sur Amoy + USDC test faucet. À faire avant M3bis.
- **ABI bundling backend** : pas encore généré. Fera partie de la première
  build avec `forge build` puis copie du JSON dans le backend.
- **Gas estimation** : le contract MVP ne fait pas d'optimisation spéciale
  (pas de packing de struct). `submitResolution` ≈ 378k gas (lu depuis les
  résultats forge test). Bonne marge vs block limit Polygon, mais à surveiller
  pour mainnet.
- **Event listener côté backend** : pas de worker qui écoute les events
  on-chain. Ce rôle sera celui du challenge bot (M4). Pour l'instant, le statut
  `dispute_status` en DB est figé à PENDING au submit et jamais mis à jour.
- **Frontend** : evidence contient maintenant 8 champs on-chain, mais pas
  encore de lien polygonscan. À ajouter en M4.
